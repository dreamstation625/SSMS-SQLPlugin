**已连接状态的实测**（`localhost,11433` / `master` / `sa`）：


**`State = Closed` 是最重要的发现**：`GetCurrentConnection()` 返回的是**连接描述（模板）**，不是活连接。

- ✅ 可读 `DataSource` / `Database` / 连接串 → 知道当前连哪台机、哪个库
- ❌ 不能直接 `ExecuteScalar` → 查元数据必须自己按该连接串另开一条
- ⚠️ 连接串里密码是明文，**日志必须脱敏**

**补齐过程**：本机 LocalDB 全部启动失败（`sqlservr.exe` 生成 dump），改用用户提供的远程实例 `localhost,11433`（经 Mihomo TUN 隧道），SSMS 连上后触发菜单探针拿到上述结果。

**对方案的影响**：补全"只当前库"的实现路径确定 —— 从 `GetCurrentConnection()` 取 `IDbConnection`，读 `Database`；用 `ConnectionChanged` / `ConnectionDisconnected` 做元数据缓存失效。方案 §5 的补全上下文推断可以按此设计。

**遗留动作**：等有可用数据库时（用户本机或远程实例），连一次查询窗口，确认 `GetCurrentConnection()` 返回非 null 且 `Database` 正确。

### S0.6 存储隔离（M0-5）— ✅ 通过（2026-11-11 13:02）

**验证目标**：SQLite 能否在 SSMS 进程里用。

**结论：能，而且不需要任何隔离。方案里「独立 AppDomain」的预判被推翻。**

SSMS 22.11 自带一整套 SQLitePCLRaw：

```
<IDE>\PublicAssemblies\SQLite\
    SQLite-net.dll
    SQLitePCLRaw.batteries_v2.dll
    SQLitePCLRaw.core.dll
    SQLitePCLRaw.provider.e_sqlite3.dll
    e_sqlite3.dll          ← native，SQLite 3.53.4
```

**实测日志**：

```
已加载 sqlite native 模块数 = 0
Batteries_V2.Init() OK
[Init 后 native] e_sqlite3.DLL @ ...\IDE\PublicAssemblies\SQLite\e_sqlite3.DLL
Init 后 sqlite native 模块数 = 4
SQLiteConnection(:memory:) OK
SELECT sqlite_version() -> 3.53.4
SELECT 1 + 1 -> 2
建表/写入/读回 OK：count=2 first=SELECT 1
已关闭连接
```

**为什么不冲突**：SSMS 用 **SQLitePCLRaw**，不是 `System.Data.SQLite`。之前担心的"native 进程级单例会撞"针对的是后者（`SQLite.Interop.dll`），SSMS 不用那套。我们也用 SQLitePCLRaw 且**不打包 native** → 共用同一个 `e_sqlite3.dll`，没问题。

**架构变更**：

| 项 | 原方案 | 实测后 |
|---|---|---|
| 存储位置 | 独立 AppDomain + 单独 .config | **普通类库即可** |
| native 来源 | 三个包各自携带 | **用宿主的，不打包** |
| 跨域 DTO | 需要 | **不需要** |
| `SsmsSqlPlugin.Storage.Isolation` 工程 | 要建 | **取消** |

**踩到的小坑**：`ExecuteScalar<T>` / `Execute` 都带 `params object[]`，反射调用时参数个数要按实际签名补 `new object[0]`，否则 `MissingMethodException`。

**对方案的影响**：存储层大幅简化，省掉一个工程和跨域序列化。方案 §6.2、项目清单、验证清单、风险表已同步修正。降级路径：宿主目录消失时用自带 native（那时才需要隔离），再不行退 append-only 日志。
