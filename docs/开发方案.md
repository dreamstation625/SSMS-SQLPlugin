## 2. 平台事实

### 2.1 三个版本的差异（这是整个架构的约束源头）

| 项 | SSMS 20 | SSMS 21 | SSMS 22 |
|---|---|---|---|
| Shell | VS 2019（16.x）Isolated | VS 2022（17.x） | VS 2026 |
| **位数** | **x86** | x64 | x64 |
| 安装路径 | `C:\Program Files (x86)\Microsoft SQL Server Management Studio 20\Common7\IDE\Extensions` | `C:\Program Files\Microsoft SQL Server Management Studio 21\Release\Common7\IDE\Extensions` | 同 21 |
| VS SDK | **15.x** | 17.x | 17.x |
| 部署方式 | **文件拷贝**（VSIXInstaller 对 IsolatedShell 支持不稳，M0 验证） | VSIX / 文件拷贝 | VSIX / 文件拷贝 |
| **补全 API** | **旧版 `ICompletionSource` + `ICompletionBroker`（同步）** | 异步管线 | 异步管线 |
| SMO / ScriptDom | 随 SSMS 20 自带（16.x 世代） | 17.x 世代 | 18.x 世代 |
| 深色主题 | **无** | 有 | 有 |
| SQLite native | x86 | x64 | x64 |
| 内存上限 | 32 位进程，**大脚本要注意** | — | — |

**结论：一个 VSIX 包不可能同时适配 20 和 22。必须出三个独立产物。**

```
SSMS-SQLPlugin.V20.vsix   (x86, VSSDK 15.x, 旧补全管线)
SSMS-SQLPlugin.V21.vsix   (x64, VSSDK 17.x, 异步补全)
SSMS-SQLPlugin.V22.vsix   (x64, VSSDK 17.x, 异步补全)
+ SSMS-SQLPlugin.Setup.exe 统一安装器（检测本机装了哪几个 SSMS，逐个投放）
```

安装器参考 SqlPilot 的做法：独立 WPF exe，不进扩展加载链，按版本号选包，卸载时保留用户数据。

### 2.2 兼容 20 到底贵在哪

| 难点 | 影响 | 应对 |
|---|---|---|
| **补全 API 完全不同** | 旧的 `ICompletionSource` 是同步、拉取式的，异步管线是流式 + 独立排序器/提交器。两套要各写一遍接线 | 候选生成逻辑 100% 共用（在 Core），只重写「怎么把列表交给编辑器」这一层。约 6 人日 |
| **32 位进程** | 格式化 5MB 脚本时 AST + token 流很容易吃掉 1GB+，可能 OOM | 超过 2MB 的脚本拒绝整篇格式化，提示「请选中片段」；AST 用完立即释放，不缓存 |
| **无深色主题** | 主题探测服务不存在 | 探测失败回退浅色，不抛异常 |
| **VSSDK 15.x** | 三个包工程不能用同一套 SDK 引用 | 分包工程 + 每个包引用自己 SSMS 安装目录的 DLL |
| **部署机制不正规** | 用户装不上 | 自建安装器 + 卸载脚本；README 写清手动路径 |

### 2.3 必须遵守的硬规则

| 规则 | 原因 |
|---|---|
| 引用 SSMS 安装目录里的 DLL，不要 NuGet 拉不同版本 | 进程内已加载同名程序集，版本不一致 → 类型标识冲突 / `MissingMethodException` |
| **三个包工程分别编译，不用 extern alias** | 各包部署到不同 SSMS、各自进程独立，分开编译最简单；把三套 adapter 编进同一个 DLL 再运行时探测（某些项目的做法）会让依赖图变成一团 |
| `SqlKit` 层（Core/Formatting/Metadata/Storage）零 SSMS 依赖 | 否则无法单测，也无法三版本共用 |
| 内部 API 全部收口到 `ISsmsHostAdapter` | SSMS 升级时只改一个实现类 |
| 按键路径禁止查库、禁止同步问宿主 | 一次宿主往返 2~7ms，忙时实测 1908ms |

### 3.2 关键接口（抽象层）

```csharp
public interface ISsmsHostAdapter
{
    bool TryGetActiveEditor(out IEditorContext ctx);          // 文本视图 + 缓冲区
    bool TryGetConnection(EditorMoniker moniker, out SqlConnectionInfo conn);
    event EventHandler<ConnectionChangedEventArgs> ConnectionChanged;
    void SubscribeExecution(IExecutionObserver observer);      // 执行前/后回调
    ICompletionPresenter CreateCompletionPresenter();          // 20 与 21/22 各自实现
    IThemeInfo Theme { get; }
    string UiCulture { get; }
}
```

`ICompletionPresenter` 是适配两套补全 API 的关键：它只定义「把 `IReadOnlyList<CompletionItem>` 交给编辑器」和「拿回提交结果」，实现由各版本包工程提供。Core 完全不感知版本差异。

## 4. 格式化引擎

### 4.1 开源库选型（你问过的问题，保留结论）

| 库 | 语言 | 许可证 | 能否用 | 原因 |
|---|---|---|---|---|
| **Microsoft ScriptDom** | C# | **MIT** | ✅ 必用，半个引擎 | 解析 + 生成；生成器**丢注释**，换行只有十几个布尔开关 |
| **SQLFluff** | Python | MIT | ❌ | 排版质量最好，但要 Python 运行时。**只能当规则参考** |
| **sql-formatter** | TS | MIT | ⚠️ 能嵌不推荐 | **不支持存储过程**——SSMS 里的高频场景 |
| **Sqruff** | Rust | Apache-2.0 | ❌ | 跨语言 |
| **Poor Man's** | C# | **AGPL-3.0** | ❌ | 传染整个项目；且 2019 年后停更，注释乱序 |

**C# 生态没有「喂字符串 → 漂亮 SQL → 保留注释 → 许可证宽松」的现成库。** ScriptDom 已经把语法树和 token 流做完了，我们只写布局这一层。

### 4.2 三阶段管线

```
SQL 文本
  ├─ ① 解析：TSqlParser → AST + TokenStream（含空白/注释 trivia）
  │        失败 → 按 GO 切 batch 逐段重试；仍失败的 batch 原样保留
  ├─ ② 建模：AST → Document IR（Group / Indent / Line / Text）
  │        注释按位置绑定：尾随 / 前置 / 行内
  └─ ③ 渲染：Wadler pretty printer，宽度预算 100，超宽自动折行
            → 输出到 ITextBuffer 编辑事务（天然支持 Ctrl+Z）
```

**为什么先建 IR 再渲染**：折行是全局决策（放不下才折，且尽量少折），只有先建树、按剩余宽度决定 flatten/break，结果才稳定。直接拼字符串只能硬折，长表达式会很难看。

**大脚本保护**：SSMS 20 是 32 位，超过 2MB 的脚本拒绝整篇格式化，提示选片段。

**工作量**：解析封装 3d + IR/printer 5d + SELECT 家族 8d + DML 4d + DDL 6d + 流程控制 4d + 配置 3d + 语料测试 5d ≈ **38 人日**。

### 4.3 风格配置

`.sqlkit.json`，字段命名对齐 SQL Prompt 习惯（降低迁移成本）：

```json
{
  "keywordCasing": "upper",
  "indentSize": 4,
  "maxLineWidth": 100,
  "commaPlacement": "trailing",
  "alignAliases": true,
  "alignColumnDefinitions": true,
  "newLineBeforeJoin": true,
  "parenthesisStyle": "expanded",
  "blankLinesBetweenStatements": 1,
  "preserveComments": true

```

查找顺序：当前目录 → 向上 5 层 → `%APPDATA%\SsmsSqlPlugin\style.json` → 内置默认。团队可把 `.sqlkit.json` 提交进仓库共享。

### 4.4 交互

| 入口 | 行为 |
|---|---|
| `Ctrl+K Ctrl+D` | 格式化全文 |
| `Ctrl+K Ctrl+F` | 格式化选区 |
| 右键菜单 / 工具栏 | 同上 |

## 5. 补全

### 5.1 两套管线，一个候选源

| 版本 | API | 特点 |
|---|---|---|
| SSMS 20 | `ICompletionSourceProvider` + `ICompletionSource` + `ICompletionBroker` | 同步、拉取式 |
| SSMS 21/22 | `IAsyncCompletionSource` + `IAsyncCompletionItemManager` + `IAsyncCompletionCommitManager` | 流式、排序/提交分离 |

**共用部分**：候选生成、上下文判定、别名解析、打分排序 —— 全在 `SsmsSqlPlugin.Core`，输出 `IReadOnlyList<CompletionItem>`。
**分叉部分**：怎么交给编辑器。约 6 人日。

### 5.2 为什么不自绘 WPF 列表

三个死结：① 和内置列表同时出现；② 只能键盘操作；③ 要反复抢 session（`DismissAllSessions`，会把用户正在用的列表踢掉）。

必须自己实现排序器的原因：平台默认匹配器没有词首感知，`libr` 排不到 `Lib_Reader`。

### 5.3 元数据

```sql
SELECT s.name AS SchemaName, o.name AS ObjectName, o.type,
       c.name AS ColumnName, c.column_id, t.name AS DataType,
       c.max_length, c.is_nullable, c.is_identity
FROM sys.objects o
JOIN sys.schemas s ON s.schema_id = o.schema_id
JOIN sys.columns c ON c.object_id = o.object_id
JOIN sys.types  t ON t.user_type_id = c.user_type_id
WHERE o.type IN ('U','V','TF','IF') AND o.is_ms_shipped = 0
```

| 关注点 | 处理 |
|---|---|
| 无 VIEW DEFINITION 权限 | 降级 `INFORMATION_SCHEMA.COLUMNS` → 再失败只出关键字 |
| 规模 | 1000 表 × 20 列 ≈ 2 万条 ≈ 10MB；超 5 万对象只预载表名 |
| 冷启动 | 打开查询窗口后台预热，按键路径只读内存 |
| 失效 | DDL 后 5 分钟刷新；`Ctrl+Shift+D` 强制刷新 |
| 跨库 | v1 不做，遇到 `db.schema.table` 直接放弃该项 |

### 5.4 上下文判定（纯逻辑，全在 Core）

| 槽位 | 判定 | 建议内容 |
|---|---|---|
| `FROM` / `JOIN` 后 | 最近关键字是 FROM/JOIN/`,` 且在表位置 | 表、视图、TVF |
| `alias.` 之后 | 前一个 token 是 `.` 且有别名映射 | 该表字段 |
| SELECT 列表 | 首关键字 SELECT 且未到 FROM | 已声明别名的字段 + 函数 |
| `EXEC` 之后 | 最近关键字 EXEC | 存储过程 + 参数 |
| 类型位置 | `CAST(x AS _)` / `DECLARE @x _` | 数据类型 |
| 默认 | — | 关键字 + 函数 |

别名与作用域：解析 FROM 建 `alias → (schema, table)`，支持显式/隐式别名、嵌套子查询层叠、CTE。临时表与表变量从**当前脚本文本**就地解析，不查库。

### 5.5 性能预算（硬指标）

| 环节 | 预算 |
|---|---|
| 补全同步部分 | < 8ms |
| 候选上限 | 200 条 |
| 首屏渲染 | < 30ms |
| 元数据刷新 | 后台，不阻塞 UI |

## 6. SQL 历史 & 文件历史

### 6.1 执行捕获（M0 必须验证）

| 方案 | 覆盖 | 缺陷 |
|---|---|---|
| A. VSCT 键绑定 + `IVsTextViewFilter` 拦 F5 | 键盘执行 | 点工具栏按钮不经过；`QueryStatus` 里只能做 GUID 比对 |
| B. `DTE.Commands` 的 `BeforeExecute` / `AfterExecute` | 键盘 + 按钮 + 菜单 | 拿不到「执行的是选区还是全文」 |
| C. 执行后从宿主服务 / 状态栏补统计 | 耗时、行数、错误号 | 只有结果没有原文 |

实践组合：**执行前抓文本（选区优先）+ 执行后抓统计，用 ExecutionId 配对**。三版本要各验一遍。

记录字段：

```
StartedUtc, DurationMs, ServerName, DatabaseName, LoginName,
ContentId(→SQL 文本), RowsAffected, Succeeded, ErrorNumber, ErrorMessage,
SourcePath, EditorMoniker, IsSelectionOnly, SsmsVersion
```

### 6.2 存储：SQLite（复用宿主自带，不打包 native）

> **2026-11-11 M0-5 实测修正**：原文写的是「独立 AppDomain 隔离」，实测证明**不需要**。下面以实测结论为准。

**实测结论**：SSMS 22.11 自带 `PublicAssemblies\SQLite\` 一整套：

```
SQLite-net.dll
SQLitePCLRaw.batteries_v2.dll
SQLitePCLRaw.core.dll
SQLitePCLRaw.provider.e_sqlite3.dll
e_sqlite3.dll            ← native，版本 3.53.4
```

在扩展里直接 `Assembly.LoadFrom` 这一套，`Batteries_V2.Init()` → 打开 `:memory:` → 建表/写入/读回**全部成功**，`e_sqlite3.dll` 只加载一份（从宿主目录），**没有冲突**。

原因：SSMS 用的是 **SQLitePCLRaw 生态**，不是 `System.Data.SQLite`。之前的"native 是进程级单例会撞"的担心，针对的是后者（有 `SQLite.Interop.dll`），SSMS 根本不用那套。**只要我们也用 SQLitePCLRaw 且不打包自己的 native，就不会撞。**

**因此**：

- **不打包** SQLite native / SQLitePCLRaw 到 VSIX，运行时用宿主目录那一份
- **不需要**独立 AppDomain、不需要单独 `.config`、不需要跨域 DTO
- 存储层放在普通的 `SsmsSqlPlugin.Storage` 类库即可

**版本风险与降级**：SQLite 版本跟随 SSMS（当前 3.53.4）。若将来某版 SSMS 改了路径或移除了这一套，降级路径：

1. 先试宿主目录 → 2. 找不到就用扩展目录里自带的（此时才需要隔离）→ 3. 都不行退到 append-only JSON 日志 + 内存索引

```sql
Contents(ContentId BLOB PK, SqlBytes BLOB, Length INT, LastSeenUtc TEXT)
Executions(Id INTEGER PK, StartedUtc TEXT, DurationMs INT, ServerName TEXT,
           DatabaseName TEXT, LoginName TEXT, ContentId BLOB, RowsAffected INT,
           Succeeded INT, ErrorNumber INT, ErrorMessage TEXT,
           SourcePath TEXT, EditorMoniker TEXT, IsSelectionOnly INT)
Files(Id INTEGER PK, FullPath TEXT UNIQUE, FirstSeenUtc, LastOpenedUtc,
      LastSavedUtc, OpenCount INT)
FileRevisions(Id INTEGER PK, FileId INT, ContentId BLOB, CapturedUtc, Kind TEXT)
FileContexts(Id INTEGER PK, FileId INT, ServerName TEXT, DatabaseName TEXT, LastUsedUtc)
Favorites(Id INTEGER PK, Name TEXT, ContentId BLOB, ServerName TEXT, DatabaseName TEXT)
SchemaCache(ServerName TEXT, DatabaseName TEXT, FetchedUtc TEXT, Payload BLOB,
            PRIMARY KEY(ServerName, DatabaseName))
```

索引：`IX_Executions_StartedUtc`、`IX_Executions_ServerDb_Time`、`IX_FileRevisions_File_Time`。
配置：WAL、`busy_timeout=5000`、**单写线程**（SQLite 只有一个写者）。
位置：`%LOCALAPPDATA%\SsmsSqlPlugin\data.db`。

### 6.3 容量与回收

| 项 | 默认 | 可配 |
|---|---|---|
| 执行历史保留 | 90 天 或 200MB | ✅ |
| 单文件快照数 | 30 个 | ✅ |
| 快照最小间隔 | 60 秒 | ✅ |
| 快照单文件上限 | 2MB（超出只存哈希） | ✅ |
| 回收 | 每日一次，按时间淘汰，空闲 VACUUM | — |

### 6.4 文件历史

- **清单**：`DocumentOpened/Saved/Closing` + RunningDocumentTable 兜底；只收 `.sql` / `.sqlplan` / `.ddl`
- **连接绑定**：打开时记下当时的服务器与库 → 能「在原来的连接下重开」；同一文件可关联多个连接
- **快照**：只在 `DocumentSaving` 抓保存前的缓冲区，SHA-256 去重后写 `Contents`
- **回滚 UI**：列表 + 两版本并排只读 diff。**不内嵌真编辑器**（HwndHost 里全是坑），需要时调外部 diff 工具
- **失效**：文件被外部删除/改名，标记「已失效」但不删记录

### 6.5 UI

1. **SQL History** — 搜索 + 服务器/库/时间筛选；列：时间、库、耗时、行数、成败、摘要；双击在正确连接下重开。`Ctrl+Shift+H`
2. **Settings** — 格式化风格、保留策略、补全开关、界面语言、AI 服务（BaseUrl / Model / Key）、诊断日志

主题：21/22 跟随系统深浅色；20 无深色主题，探测失败回退浅色。

## 8. AI 改写 / 解释

> 定位：**纳入 v1**（不是预留）。两个入口，不做对话式面板，不做 Agent。

### 8.1 做什么

| 入口 | 行为 |
|---|---|
| 选中 SQL → 右键「AI 改写」 | 按选定意图重写（加注释 / 改 CTE / 拆子查询 / 换 JOIN 写法 / 自定义提示），结果进 diff 预览，点「应用」才替换 |
| 选中 SQL → 右键「解释这段 SQL」 | 只读浮层输出，不碰编辑器 |

### 8.2 协议：只做 OpenAI 兼容

不自研模型，也不为每家写适配器。统一走 `POST {BaseUrl}/v1/chat/completions`，一个实现覆盖：

- **本地**：LM Studio、Ollama（兼容层）、vLLM
- **云端**：DeepSeek、通义千问（兼容模式）、Kimi、智谱、OpenAI、Azure OpenAI

用户在设置里填 `BaseUrl` + `Model` + `ApiKey` 三项即可，不做模型列表硬编码（用 `/v1/models` 拉取，失败则手填）。

### 8.3 接口

```csharp
namespace SsmsSqlPlugin.Core.Assistant;

public interface ISqlAssistantProvider
{
    string Id { get; }                    // "openai-compatible"
    string DisplayName { get; }
    bool IsConfigured { get; }            // BaseUrl / Model 齐了才算
    Task<RewriteResult> RewriteAsync(RewriteRequest request, CancellationToken ct);
    Task<string> ExplainAsync(ExplainRequest request, CancellationToken ct);
}

public sealed record RewriteRequest(
    string Sql,
    string Intent,                 // 预置意图 id 或用户自定义提示
    string? SchemaContext,         // 可空；仅在用户勾选时填充
    int MaxTokens);

public sealed record RewriteResult(
    string Sql,
    string? Explanation,
    string Model,
    int PromptTokens,
    int CompletionTokens);
```

`ISqlAssistantProvider` 在 DI 里按 Id 注册，默认实现 `OpenAiCompatibleProvider`。换协议只需新增一个类，不动调用方。

### 8.4 隐私与安全（这一节比功能本身重要）

SQL 里有表名、字段名、注释，经常还有硬编码的连接信息。外发必须极其克制：

| 措施 | 具体做法 |
|---|---|
| **默认不可见** | 未配置时不显示任何 AI 菜单项，不弹引导、不推销 |
| **首次使用明示** | 第一次点 AI 命令弹一次确认：「SQL 文本将发送到 `<BaseUrl>`」，确认后才发，记在设置里不再重复 |
| **默认不带元数据** | 只发选中的 SQL。「附带表结构」是单独勾选项，且体积上限 32KB、只发表名/列名/类型，不发数据 |
| **密钥不落明文** | ApiKey 用 Windows DPAPI（`ProtectedData.Protect`，CurrentUser 范围）加密后存 `%APPDATA%\SsmsSqlPlugin\secrets.dat` |
| **本地地址免提示** | `BaseUrl` 是 `localhost` / `127.0.0.1` / `::1` 时跳过外发确认（但仍记日志） |
| **日志脱敏** | 诊断日志里 SQL 只记 ContentId 与长度，ApiKey 一律 `***` |
| **超时与取消** | 默认 60s 超时，可取消；失败只在状态栏提示，原文一个字不动 |

### 8.5 结果落地

- **改写**：结果不直接替换，先出并排 diff（复用 §6.4 的只读 diff 控件）。用户点「应用」→ 走 `ITextBuffer` 编辑事务 → 天然支持 `Ctrl+Z`。
- **解释**：只读浮层，跟随鼠标位置，`Esc` 关闭。
- **模型输出必须清洗**：剥掉 ```sql 围栏、剥掉前后解释文字；若解析不出唯一 SQL 块，直接给原文让用户自己判断，不猜。

### 8.6 成本：3.5 天

| 项 | 天 |
|---|---|
| 接口 + `OpenAiCompatibleProvider`（含重试、超时、SSE 解析） | 1 |
| 设置页 AI 分组（BaseUrl/Model/ApiKey/测试连接/附带元数据开关） | 1 |
| 命令表 + 右键菜单 + 意图清单 | 0.5 |
| diff 预览与落地 | 0.5 |
| 错误处理、脱敏日志、首次确认弹窗 | 0.5 |

> 这笔账要算清楚：**加 AI 不是 3.5 天的事**。真上线后会有模型输出质量、prompt 调优、各家兼容性差异的持续投入。v1 只做「能跑通、可替换、隐私可控」的最小闭环，不做 prompt 工程比赛。

## 12. 风险登记

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
