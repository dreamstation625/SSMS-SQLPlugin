## S3.1 SQLite 存储层 — ✅ 已完成（2026-11-12）

### 结构

| 位置 | 职责 |
|---|---|
| `src/SsmsSqlPlugin.Storage/SqliteHost.cs` | 反射加载宿主 `PublicAssemblies\SQLite` 的 SQLitePCLRaw + SQLite-net；不引用/不打包 native |
| `StorageDatabase.cs` | 单写线程队列、WAL/busy_timeout、schema、执行记录写入与查询、内容哈希去重 |
| `StorageSchema.cs` | Contents / Executions / Files / FileRevisions / FileContexts / Favorites / SchemaCache + 索引 |
| `ExecutionRecord.cs` | 执行历史 POCO（字段对应 §6.1） |
| `tools/StorageCli/` | 独立回归：1000 写、WAL、去重、杀进程恢复 |

- DB 位置：`%LOCALAPPDATA%\SsmsSqlPlugin\data.db`
- 宿主加载顺序：`SQLitePCLRaw.core` → `provider.e_sqlite3` → `batteries_v2` → `Batteries_V2.Init()` → `SQLite-net`
- 所有 DB 操作都在专用后台线程；UI 通过 `Task` 调用。
- 内容去重：SQL 文本 UTF-8 SHA-256 → `Contents.ContentId`，相同 SQL 只存一份。
- 启动时 `PRAGMA journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`。
- CLI 进程额外注册 `AssemblyResolve`，从宿主 `PublicAssemblies` 解析 `System.Memory` 等依赖；SSMS 内有自己的绑定重定向，这个 handler 也无害。

### 验收证据（2026-11-12）

```

1000 次写入: 104ms
Executions=1000 Contents=1000
重复 SQL 后: Executions=1001 Contents=1000
最近记录数: 3 first=SELECT 999 AS n

[PASS] S3.1 基本存储回归

杀进程后恢复记录数: 53
[PASS] 杀进程后数据可恢复
```

### 踩到的坑

1. **`PRAGMA busy_timeout=5000` 会返回新值**，必须用 `ExecuteScalar<long>`；用 `Execute` 会报 `not an error`。
2. CLI 没有 `SSMS.exe.config` 的绑定重定向，`SQLite-net` 依赖的 `System.Memory` 需要从宿主 `PublicAssemblies` 解析。
3. 不打包 SQLite/native：`SQLiteHost` 只 `LoadFrom` 宿主目录，避免 native 单例冲突。

### 遗留

- `SsmsSqlPlugin.Storage` 还没有被 VSIX 引用；S3.2 接线时加入工程和 `build.py` 载荷。
- 文件清单/快照表和模型已建，但尚未接线。
- 回收策略（S3.5）未实现。

## S3.2 执行捕获 — ✅ 已完成（2026-11-12）

### 实现

| 位置 | 职责 |
|---|---|
| `History/HistoryRuntime.cs` | 持有唯一 `StorageDatabase`；后台打开、启动时按 24h 间隔跑回收 |
| `History/ExecutionCapture.cs` | DTE `BeforeExecute/AfterExecute` + 编辑器 F5 回调；选区/全文、连接、文件路径、耗时配对 |
| `Editor/EditorCommandFilter.cs` | 增加执行回调（VSStd2K/0x0067），只观察不拦截 |
| `Storage/StorageDatabase.cs` | 开始时插入记录拿 Id，结束后按 Id 补写 `DurationMs` |

- 命令识别不硬编码 Query GUID：F5 用实测的 `VSStd2K/0x0067`，其余按 DTE 命令名（`Query.Execute` / `*.Execute`，排除 Cancel）。
- 两条入口（编辑器 F5、DTE）用「同视图 + 同 SQL + 1.5 秒内 + 不同来源」去重，避免一次执行记两条。
- 文本在执行前抓：选区优先，无选区取全文；`IsSelectionOnly` 落库。
- 服务器/库/登录名来自 `CompletionRuntime.Connection`；编辑器路径优先 `ConnectionDescriptor.EditorMoniker`（未保存查询是 %TEMP%，不当成用户文件）。
- 统计未知时 `Succeeded=-1`、`RowsAffected=0`，历史窗口显示“未知/—”，**不伪造成失败**。

### 验收证据（SSMS 22.11 实测）

- F5 / 工具栏 / 选区三种方式都能正确配对。
- 工具栏与 F5 走同一条 DTE 命令；编辑器 F5 回调保留作 DTE 不可用时的兜底。

### 偏离与遗留

- **拿不到行数/成败**：SSMS 22 没有稳定的执行结果 API；按方案 §7 的降级出口，只记文本/时间/连接，`Succeeded=-1`。不解析结果网格。
- 未加 `SsmsVersion` 字段（后续需要时扩表 + 迁移）。
- 未区分“执行当前语句”（Ctrl+Enter）：该命令的选区语义不同，当前只覆盖 F5 / 工具栏 / 菜单执行。

## S3.3 SQL 历史窗口 — ✅ 已完成（2026-11-12）

- 入口：顶部菜单 `SSMS-SQLPlugin → SQL 历史...`。
- 搜索框（350ms 防抖 + Enter/查询按钮）、服务器/库/时间范围筛选；服务器切换时联动库列表。
- 列：时间、服务器、库、耗时、行数、结果、摘要；VirtualMode，结果上限 2000 条。
- 右侧预览：选中行显示完整 SQL + 时间/连接/耗时/结果；自动选中首行；超过 **10 万字符**只预览前 10 万并提示，复制/打开仍是完整 SQL。
- 删除/回收站：支持多选软删除；「回收站」查看、恢复；保留 30 天后由每日回收彻底删除；回收站列表显示删除时间。
- 「打开目录」直接打开历史库所在目录（`%LOCALAPPDATA%\SsmsSqlPlugin`）。
- 双击/回车/「打开 SQL」：新建查询窗口并插入 SQL；库与当前连接不同时自动加 `USE [库];`；服务器不同先弹确认。
- 复制 SQL、刷新（重新读筛选项 + 数据）、关闭。
- 存储查询：`SearchExecutionsAsync`，SQL 文本用 `instr(lower(CAST(...)))`，服务器/库/时间走 WHERE；`Limit` 默认 2000。

## S3.4 文件清单与保存快照 — ✅ 已完成（2026-11-12）

### 实现

- RDT 事件：`OnAfterFirstDocumentLock` 记录文件打开 + 连接上下文；`OnAfterSave` 读取磁盘内容抓快照。
- 只收真实用户文件：`.sql/.sqlplan/.ddl`，排除 `%TEMP%` 下的未保存查询。
- 去重与上限：连续相同内容不落版本；`SnapshotMinIntervalSeconds=60`；每文件最多 30 版；单版 >2MB 只存 SHA-256（`Contents.SqlBytes` 为空，`Length` 保留原值）。
- `Files` 行不因文件被删除/改名而删除 —— 失效文件仍保留清单和历史版本。
- RDT 对同一文件会连发多次 first-lock，打开计数 10 秒内只算一次。

- 两次保存间隔小于 60 秒只留第一版，这是设计行为；需要更密的历史时调小 `SnapshotMinIntervalSeconds`。

## S3.5 回收策略 — ✅ 已完成（2026-11-12）

- 默认：执行历史 90 天、库 200MB、每文件 30 版、快照最小间隔 60 秒、单版 2MB。
- 每日最多跑一次：`Meta.LastRetentionUtc` 记录时间，包启动时后台检查。
- 回收站 30 天：`DeletedUtc` 软删除，到期彻底删除并清孤儿 Contents；正常历史与体积淘汰都不会误删回收站里的最新记录。
- 时间淘汰：删 90 天前执行记录；文件版本只删旧版，每文件保留最新一份；孤儿 Contents 一并清。
- 体积淘汰：按 `page_count - freelist_count` 估算有效体积，从最旧记录分批删；**至少保留最新 50 条**，避免删掉正在用的记录。
- 有较多空闲页或仍超限时 `VACUUM`；WAL 模式下 VACUUM 后再 `wal_checkpoint(TRUNCATE)`，否则文件不会真正缩小。

### 验收证据

```
写入记录: 5000 体积=3288KB
时间回收: 删除=2500 剩余=2500 内容删除=2500
体积回收: 删除=2450 剩余=50 VACUUM=True 体积=140KB
版本数: 5 -> 5
最新记录保留: True
[PASS] S3.5 回收策略
```

### 踩到的坑

1. `PRAGMA wal_checkpoint(TRUNCATE)` 返回一行结果，必须用 `ExecuteScalar<long>`。
2. VACUUM 在 WAL 模式下结果先写入 `-wal`，不追加一次 checkpoint 时数据库文件看起来没变小。
3. 体积淘汰不能按文件大小循环判断：删除后文件大小要等 VACUUM 才变；循环条件改用有效页数，否则会把最新记录也删光。

## S3.6 自动记录（不执行也记）— ✅ 已完成（2026-11-12）

### 实现

- 菜单 `SSMS-SQLPlugin → 自动记录`：关闭 / 修改后记录 / 每 1 / 5 / 15 / 30 分钟；默认 **修改后记录**。
- 设置存 `%LOCALAPPDATA%\SsmsSqlPlugin\autosave.cfg`（`enabled/mode/interval`），菜单显示当前模式并打勾。
- 后台每 **30 秒**检查当前活动 SQL 编辑器：
  - 修改后记录：内容有变化才落，最多每分钟一条；
  - 定时：内容有变化才落，间隔按设置；
  - 首次看到某个编辑器会先落一条基线。
- 只处理活动 SQL 编辑器，取全文（忽略选区），SHA-256 按编辑器去重；超过 2M 字符跳过并写一次日志。
- 自动记录和手动执行共用 `Executions` 表，新增 `Kind` 列：
  - `execute` = 手动执行；`edit` = 修改后自动记录；`timer` = 定时自动记录。
- 历史窗口新增「类型」列和类型筛选，以及「文件名」列（列表只显示文件名）；自动记录没有耗时/结果，显示“—”。
- 本地文件路径同时写入 `SourcePath` / `EditorMoniker`；未保存查询只写临时 moniker，`SourcePath` 为空。**列表只显示文件名，预览区显示完整路径**。
- 自动记录同样支持删除、回收站、30 天清理和 90 天/200MB 保留策略。

### 验收证据

```
[历史] 自动记录已启动: 修改后记录
[历史] 自动记录(修改): 长度=32 ... 文件=C:\...\Temp\SQLQuery1.sql
[历史] 自动记录(修改): 长度=45 ... 文件=H:\...\snapshot-test.sql
[历史] 自动记录(定时): 长度=58 ... 文件=H:\...\snapshot-test.sql

DB: #6 kind=edit  src=— mon=Temp\SQLQuery1.sql
    #7 kind=edit  src=H:\...\snapshot-test.sql
    #8 kind=timer src=H:\...\snapshot-test.sql
同内容静置 12 秒：记录数不变（6→6）
类型筛选：自动记录 → 2 条（修改）；全部 → 8 条（执行/修改/定时）
```

### 说明

- 自动记录不等于执行记录，失败/行数/耗时都显示“—”，避免误导。
- 只在 SSMS 的活动编辑器上工作；后台未激活的查询窗口不会持续扫描。
